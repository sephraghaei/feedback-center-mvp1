# ساو (SAV) - فاز ۱

ساو یک پلتفرم B2B2C اعلان است: کسب‌وکارها اعلان منتشر می‌کنند و مخاطبان با دنبال کردن کسب‌وکار یا موضوع، اعلان‌ها را در فید، مرکز اعلان و ایمیل دریافت می‌کنند.

این فاز شامل فید عمومی، جست‌وجو، دنبال کردن، ذخیره اعلان، مرکز اعلان، تنظیمات کانال، پنل کسب‌وکار، پنل مدیریت و ارسال ایمیل با کران است.

## استک

- Next.js 16 (App Router) و TypeScript
- Tailwind CSS v4 با توکن‌های طراحی در `app/globals.css`
- Supabase (Postgres, Auth, RLS) با اسکیمای اختصاصی `sav`
- Resend برای ایمیل
- Vercel Cron برای پردازش صف ایمیل

## راه‌اندازی

۱. نصب وابستگی‌ها:

```bash
cd sav
npm install
```

۲. فایل محیطی:

```bash
cp .env.example .env.local
```

سپس مقادیر پروژه Supabase خودت را در `.env.local` بگذار. `SUPABASE_SERVICE_ROLE_KEY` فقط سمت سرور خوانده می‌شود و هرگز به مرورگر نمی‌رود.

۳. اجرای مهاجرت روی دیتابیس:

```bash
psql "$SUPABASE_DB_URL" -f supabase/migrations/20261114000100_sav_phase1.sql
```

اگر Supabase CLI را به پروژه وصل کرده‌ای، `supabase db push` هم کار می‌کند. آدرس `SUPABASE_DB_URL` باید از session pooler استفاده کند. برای پروژه فعلی `aws-1-eu-west-1.pooler.supabase.com:5432` کار می‌کند و هاست مستقیم `db.<ref>.supabase.co` در دسترس نبود.

مهاجرت خودش اسکیمای `sav` را به PostgREST معرفی می‌کند:

```sql
alter role authenticator set pgrst.db_schemas = 'public, storage, graphql_public, sav';
notify pgrst, 'reload config';
notify pgrst, 'reload schema';
```

۴. داده نمونه:

```bash
npm run seed
```

اسکریپت یک مدیر، سه کسب‌وکار فعال، سه کاربر، چهار دنبال‌کردن و پانزده اعلان می‌سازد. اجرای دوباره آن اعلان‌های همین کسب‌وکارها را بازسازی می‌کند.

۵. اجرای برنامه:

```bash
npm run dev
```

برنامه روی `http://localhost:3100` بالا می‌آید.

## متغیرهای محیطی

| متغیر | کاربرد |
| --- | --- |
| `NEXT_PUBLIC_SITE_URL` | آدرس پایه برای لینک ورود و لینک داخل ایمیل |
| `NEXT_PUBLIC_SUPABASE_URL` | آدرس پروژه Supabase |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | کلید عمومی برای مرورگر |
| `SUPABASE_SERVICE_ROLE_KEY` | فقط برای کران ایمیل و اسکریپت‌ها، سمت سرور |
| `RESEND_API_KEY` | کلید Resend؛ اگر خالی باشد کران ایمیلی نمی‌فرستد |
| `RESEND_FROM` | فرستنده ایمیل، باید در Resend تایید شده باشد |
| `CRON_SECRET` | رمز Bearer برای `/api/cron/notify` |
| `SUPABASE_DB_URL` | فقط برای اجرای مهاجرت، در زمان اجرای برنامه استفاده نمی‌شود |

## احراز هویت

ورود فقط با لینک ایمیل و بدون رمز عبور است. در پنل Supabase این مقادیر را تنظیم کن:

- Authentication > URL Configuration > Site URL: آدرس واقعی سایت
- Redirect URLs: `http://localhost:3100/**` و دامنه تولید
- Authentication > Email: قالب لینک ورود و SMTP یا سرویس ایمیل پیش‌فرض Supabase

حساب‌های نمونه با دامنه `.example` ساخته می‌شوند و ایمیل واقعی دریافت نمی‌کنند. برای ورود به آن‌ها از Supabase Dashboard > Authentication > Users > Generate link استفاده کن، یا قبل از seed ایمیل‌های واقعی را در `scripts/seed.mjs` جایگزین کن.

## صف ایمیل

با اولین انتشار یک اعلان، تریگر دیتابیس گیرندگان را می‌سازد:

- دنبال‌کننده‌های کسب‌وکار
- دنبال‌کننده‌های موضوع‌های اعلان

برای هر گیرنده، کانال‌ها از `notification_preferences` خوانده می‌شوند. ردیف `in_app` بلافاصله `sent` می‌شود و ردیف `email` در وضعیت `pending` می‌ماند. تغییر وضعیت یک اعلان منتشرشده به منتشرشده دوباره اعلان نمی‌سازد.

کران هر دقیقه مسیر زیر را با هدر `Authorization: Bearer $CRON_SECRET` صدا می‌زند:

```
GET /api/cron/notify
```

حداکثر ۲۵ ایمیل در هر اجرا، تا سه تلاش برای هر ردیف و ذخیره خطای آخر در `last_error`. روی پلن Hobby ورسل زمان‌بندی دقیقه‌ای مجاز نیست. در آن حالت از یک زمان‌بند بیرونی یا بازه بلندتر استفاده کن.

## مسیرها و دسترسی

| مسیر | دسترسی |
| --- | --- |
| `/feed`, `/search`, `/b/[slug]`, `/topics/[slug]`, `/a/[id]` | عمومی، فقط محتوای منتشرشده و کسب‌وکار فعال |
| `/following`, `/saved`, `/notifications`, `/preferences` | کاربر واردشده، فقط ردیف‌های خودش |
| `/manage` و `/manage/[id]/...` | عضو کسب‌وکار، ۴۰۴ برای غیرعضو |
| `/admin` | فقط `platform_admin`، ۴۰۴ برای بقیه |

## امنیت و RLS

- RLS روی همه جدول‌های `sav` فعال است. مهمان فقط اعلان منتشرشده، کسب‌وکار فعال و موضوع‌ها را می‌بیند.
- دنبال‌کردن، ذخیره‌ها، تنظیمات و اعلان‌های هر کاربر فقط برای خودش قابل خواندن است.
- تریگرها تغییر نقش کاربر و ستون‌های `status` و `urgent_allowed` کسب‌وکار را برای غیرمدیر می‌بندند.
- تریگر انتشار، اعلان `urgent` را برای کسب‌وکار بدون `urgent_allowed` با خطای دیتابیس رد می‌کند.
- کلید سرویس‌رول فقط در `app/api/cron/notify` و اسکریپت‌های محلی استفاده می‌شود.

آزمون خودکار:

```bash
npm run typecheck
npm run verify:rls
```

## ASSUMPTIONS

1. ساو داخل همین مخزن و در پوشه `sav/` ساخته شده تا پروژه فیدبک‌سنتر دست نخورد. Supabase جداگانه با اسکیمای `sav` استفاده می‌شود.
2. رابط دو زبانه فارسی و انگلیسی است، فارسی پیش‌فرض است و زبان با کوکی `sav-locale` عوض می‌شود. مسیرها پیشوند زبان ندارند.
3. ورود فقط magic link است. حساب‌های نمونه با دامنه `.example` هستند و برای ورود واقعی باید ایمیل جایگزین شود یا از لینک تولیدشده در داشبورد Supabase استفاده شود.
4. ساخت کسب‌وکار خودخدمت است و کسب‌وکار تازه با وضعیت `pending` شروع می‌کند. تا تایید مدیر در فید و صفحه عمومی دیده نمی‌شود.
5. فقط مدیر پلتفرم می‌تواند وضعیت کسب‌وکار و `urgent_allowed` را تغییر دهد. اعضا پروفایل و اعلان‌ها را مدیریت می‌کنند.
6. محدودیت اعلان فوری در دیتابیس اعمال می‌شود، نه فقط در رابط کاربری.
7. فن‌اوت هنگام اولین انتشار در تریگر دیتابیس انجام می‌شود. گیرنده‌ها اجتماع دنبال‌کننده‌های کسب‌وکار و موضوع هستند و کانال‌ها از تنظیمات هر کاربر خوانده می‌شود.
8. پیش‌فرض کانال‌ها: عادی فقط درون برنامه، مهم و فوری درون برنامه و ایمیل. کاربر می‌تواند هر سطح را تغییر دهد.
9. ایمیل با Resend و کران دقیقه‌ای ورسل ارسال می‌شود. زمان‌بندی دقیقه‌ای به پلن Pro نیاز دارد. اگر `RESEND_API_KEY` خالی باشد ردیف‌های ایمیل در وضعیت `pending` می‌مانند و کران بدون ارسال پاسخ موفق می‌دهد.
10. متن ایمیل فارسی و راست‌به‌چپ است چون زبان به ازای هر کاربر ذخیره نمی‌شود و فقط در کوکی مرورگر است.
11. جست‌وجو با `ilike` روی عنوان و متن و با فیلتر موضوع، کسب‌وکار، بازه تاریخ و اهمیت انجام می‌شود. نتیجه حداکثر ۱۰۰ مورد است و ایندکس جست‌وجوی متنی کامل ندارد.
12. حذف اعلان توسط مدیر نرم است و وضعیت را به `removed` می‌برد. حذف فیزیکی انجام نمی‌شود.
13. لوگو فقط آدرس تصویر است و آپلود فایل یا Storage در این فاز وجود ندارد.
14. صفحه‌بندی در فاز ۱ نیست و هر لیست سقف ۳۰ تا ۶۰ ردیف دارد.
15. `NEXT_PUBLIC_SITE_URL` باید با Site URL و Redirect URLs در Supabase هماهنگ باشد وگرنه لینک ورود به آدرس اشتباه می‌رود.
16. تاریخ‌ها با `Intl` و لوکال `fa-IR` یا `en-US` نمایش داده می‌شوند.
17. داده نمونه نهایی شامل مدیر `admin@sav.example`، کاربران `sara@`، `reza@` و `mina@` با دامنه `sav.example` است. فروشگاه توسکا عمدا `urgent_allowed=false` دارد تا رد شدن اعلان فوری قابل آزمون باشد.
18. شماره تلفن، پیامک، پوش، کامنت، لایک، زیردامنه، ویجت، آنالیتیکس، پرداخت و هوش مصنوعی خارج از فاز ۱ هستند.

## وضعیت پذیرش

- مهمان می‌تواند `/feed` و `/b/[slug]` را باز کند: تاییدشده
- اعلان درون‌برنامه‌ای با اولین انتشار ساخته می‌شود و ایمیل در صورت اجازه تنظیمات در صف قرار می‌گیرد: تاییدشده در تریگر و `verify:rls`
- کسب‌وکار بدون `urgent_allowed` نمی‌تواند اعلان فوری منتشر کند: تاییدشده با خطای `urgent_not_allowed`
- هر کاربر فقط ردیف‌های خودش را می‌خواند: تاییدشده با حساب دوم و `verify:rls`
- `/manage` برای غیرعضو و `/admin` برای غیرمدیر بسته است: بررسی مهمان با ریدایرکت و بررسی سطح داده با RLS انجام شده؛ آزمون کلیک‌محور با نشست واقعی به محیط ایمیل نیاز دارد
- متن فارسی و RTL در همه صفحه‌های عمومی: تاییدشده در عرض ۳۹۰ و ۱۴۴۰ پیکسل بدون سرریز افقی و بدون هم‌پوشانی با نوار پایین موبایل

پیامک، اعلان پوش، کامنت، لایک، زیردامنه اختصاصی، ویجت، آنالیتیکس، پرداخت و قابلیت‌های هوش مصنوعی.
